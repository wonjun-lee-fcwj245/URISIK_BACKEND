## 1. 한 줄 요약

- **동시 리뷰 교착은 재현됐다.** INSERT 후 UPDATE 구조에서 100명이 같은 레시피에 리뷰하면 **94건(92~95)이 교착으로 실패**했고, UPDATE를 먼저 실행하도록 바꾸면 **0건**이다(5회). 다만 기존 주장의 "85건"·"15→100건"과는 숫자가 다르다.
- 재검증 중 **평균 별점이 실제 점수의 절반으로 저장되는 버그**를 발견해 수정했다(`0914ab8`). 수정 후에도 남는 반올림 누적 오차(리뷰 2,000건 동시에 레시피 20개 중 12~13개의 평균이 어긋남)는 **점수 합계를 저장하면 0이 됨**을 확인했다.
- 같은 코드에서 **락 순서만 바꾼 비교**에서 FOR UPDATE 대비 UPDATE 먼저는 경합 시 p95가 **14~16% 낮다**(기존 "4.65 → 0.92초"는 재현되지 않음).
- **재시도는 설계를 잘하면 거의 성공시키지만 비용이 크다.** 같은 트랜잭션 안 재시도는 구조상 불가능하고(rollback-only), 트랜잭션 밖에서 10회 지수 백오프 재시도는 98/100까지 가지만 p95가 6.4초(락 순서 변경은 1.6초)이고 일부는 여전히 실패한다. 락 순서를 바꾸면 100/100, 교착 0건이다(새로 구현한 비교 실험).
- **ES+Nori의 이유는 속도가 아니라 오타 보정이다.** 5,000건에서는(외부 API를 stub으로 바꿔도) LIKE·FULLTEXT보다 빠르지 않고(ES가 가장 느림), 자모 1~2곳 오타 정답률이 LIKE/FULLTEXT 0~9%인 반면 ES+자모는 94~100%다.
- **Redis가 중단되면 추천 API가 오류 없이 매달린다**(40건 모두 30초 타임아웃). 캐시 적중 시 응답은 약 4~6배 빠르다.
- **튜닝은 높은 부하에서 효과가 있었다(재설계 측정).** 기본값은 약 550 RPS까지 SLO(p95 1초)를 지키고 600에서 0/3으로 무너졌고(Hikari 풀 포화, 대기 198), 전체 튜닝(Hikari 50 + Tomcat 500)은 600 RPS에서 3/3 통과(p95 590ms)했다. Hikari 풀만 키운 설정은 기본값보다 나아지지 않았고, 600 RPS 이상의 한계는 측정하지 못했다. 포화 구간 실패는 모두 지연·드롭이고 5xx·연결 실패는 0건이었다(1차 측정의 연결 거부는 포트 포워딩 경로 문제였다).

### 정합성

- **리뷰·찜 카운터와 실제 행 수**: 실험 1 전체 155회(v0 50, v3 50, v1 15, v4 25, 재시도 비교 15) 모두 일치했다. 실패한 요청은 롤백되어 카운터가 틀어지지 않는다.
- **평균 별점 버그**: v3에서 레시피당 리뷰 1건일 때(시나리오 B) **100개 중 100개가 불일치**했다(예: 4점 → 2점으로 저장). v4에서 **0개**.
  - 원인: MySQL은 `UPDATE … SET a = …, b = …`를 왼쪽부터 평가해, `reviewCount`를 먼저 올리면 평균 계산에 증가된 값이 쓰인다. `dd06895`에서 두 UPDATE를 합칠 때 들어갔다(v1도 같은 쿼리, B 시나리오는 v1을 측정하지 않았다).
  - 남은 오차: 100건이 쌓일 때 반올림 누적으로 평균이 0.1~0.2 어긋난다(v4 최대 0.1~0.2). 이 오차를 **점수 합계(`score_sum`) 컬럼으로 해결**할 수 있는지 아래 「평균 별점 누적 오차 검증」에서 측정했다.

### 평균 별점 누적 오차 검증 (점수 합계 저장)

v4의 평균 갱신은 반올림된 평균에 다시 곱하고 더해 새 평균을 만든다(`ROUND((avg × n + s) / (n + 1), 1)`). 반올림 오차가 매 리뷰마다 쌓인다. 점수 합계(`score_sum`)를 저장하고 평균을 `ROUND(합계 / 개수, 1)`로 계산하면 오차가 쌓이지 않는다. v4 위에 컬럼 하나와 UPDATE 쿼리만 바꾼 변형(`s`, 패치 `scripts/lock-variants/score-sum-on-0914ab8.patch`, 메인 코드에는 넣지 않음)을 같은 조건으로 비교했다. **사용자 100명이 레시피 20개에 각자 리뷰 1건씩(2,000건)을 동시에 작성**하고 저장된 값을 실제 집계와 비교했다. 점수는 (사용자, 레시피)로 정해지는 결정적 값(1~5)이고 3세트(서로 다른 레시피 20개씩, 총 6,000건)를 반복했다.

| 변형 | 리뷰 수 불일치 | 평균 불일치(`ROUND(AVG)`와 다름) | 실제 평균과 최대 오차 | 점수 합계 불일치 |
|---|---|---|---|---|
| v4 (평균을 반올림해 누적) | 0 / 60 | **12~13 / 20 (세트마다)** | **0.2** | |
| **s (점수 합계 저장)** | 0 / 60 | **0 / 60** | **0.0** | 0 / 60 |

- v4는 리뷰 수는 정확하지만 레시피의 약 60~65%에서 평균이 어긋난다. 점수 합계를 저장하면 같은 조건에서 **불일치 0, 오차 0**이 된다. 컬럼 하나(`score_sum BIGINT`)와 UPDATE 쿼리 변경이 전부다.
- 기존 데이터에는 `score_sum`을 `ROUND(avg_score × review_count)`로 채우는 이전 작업이 필요하다(이번 실험은 대상 레시피를 0으로 초기화해 쓰므로 해당 없음).
- 이 변형은 실험용이며 메인 코드에는 아직 반영하지 않았다.

### 락 순서만 바꾼 재비교 (같은 코드, 지연 비교의 근거)

앞의 v0·v1·v3 비교는 서로 다른 커밋이라 락 순서 외의 코드 차이가 섞여 있다(시나리오 B에서도 p95가 달랐던 이유). 그래서 v4 코드 위에 **락 획득 순서만 바꾸는 모드**를 환경변수로 넣어(`scripts/lock-variants/lock-modes-on-0914ab8.patch`, 메인 코드에는 넣지 않음) 다시 쟀다. 모드 3가지가 같은 쿼리를 쓰고 순서만 다르다: `insert_first`(INSERT → UPDATE), `for_update`(SELECT FOR UPDATE → INSERT → UPDATE), `update_first`(UPDATE → INSERT). 5라운드, 라운드마다 모드 순서 회전, 1회차 워밍업 제외(4회), 레시피 ID 풀은 DB를 기준 시드로 복원한 뒤 새로 시작했다.

### 추가 실험: 재시도 방식 비교 (새로 구현, 옛 "58/100"의 재현이 아님)

`0e223cf`(v0) 위에 재시도 모드를 환경변수로 켜는 코드를 별도 worktree에서 구현했다(패치: `scripts/retry-variants/`, 메인 코드에는 넣지 않음). 같은 레시피에 100명 동시 리뷰, 구성별 5회(1회차 워밍업 제외, 같은 트랜잭션 안·고정 대기 `inside3fixed`는 전체 로그를 남기려고 3회 중 2회 집계). "58/100"을 낸 원래 코드는 커밋된 적이 없어 같은 코드인지 확인할 수 없다. **재시도 설계(대기 방식)에 따라 결과가 크게 달라서 두 번에 나눠 측정했다**: 1차는 고정 짧은 대기(10~50ms), 2차는 지수 백오프(50→100→200→400→800→1600ms 상한 + 0~50ms 지터)다.

|---|---|---|---|---|---|
| 재시도 없음 (v0) | 6 (5~8) | 94 | 924 (876~1261) | 1,189 / 1,267 | 0 |
| 같은 트랜잭션 안, 3회, 고정 대기 | 8 (7~8) / 5 (4~6) | 260 / 264 | 1,078 / 1,012 | 1,091 / 1,062 | 0 |

- **같은 트랜잭션 안 재시도는 구조상 성공할 수 없다.** 재시도 때마다 트랜잭션 상태를 기록했더니 262번 전부 `rollbackOnly=true`였다. 교착 예외가 저장소 호출을 지나는 순간 Spring이 트랜잭션을 롤백 전용으로 표시하기 때문이다. 교착을 겪은 요청 96건 중 81건은 3회를 소진해 실패했고, 나머지 15건은 재시도가 성공한 것처럼 보였지만 **커밋 단계에서 `UnexpectedRollbackException`(15건)으로 실패**했다(96 = 81 + 15). 앞선 보고서의 "`UnexpectedRollbackException` 0건"은 오류 줄만 걸러 저장한 로그에서 센 값이라 틀렸고, 전체 로그로 정정한다.
- **밖에서 재시도하면 성공이 늘고, 대기 설계가 결과를 좌우한다.** 고정 짧은 대기로는 10회에도 66건이지만 지수 백오프 10회는 98건(95~100)까지 올라간다. 즉 "재시도는 10회로도 66건뿐"이라는 결론은 고정 대기 구현에 한정된다.
- **백오프의 누적 대기를 함께 읽어야 한다.** 지수 백오프(50, 100, 200, 400, 800, 1,600ms 상한)로 10회 시도하면 대기 합계가 최대 `50+100+200+400+800+1,600×4 = 7,950ms`(+지터 최대 약 0.45초)다. 3회 시도는 합계 150ms다. 10회 구성의 p95 6.4초는 상당 부분 이 **의도된 대기 시간**이고, 재교착으로 인한 지연과 분리해서 측정하지는 못했다. 상한이 더 짧은 백오프를 쓰면 성공률과 p95가 다르게 나올 수 있다.
- **그래도 락 순서 변경이 낫다.** 지수 백오프 10회 재시도는 일부(최대 5건)가 여전히 실패하고, 교착 시도가 294건이며, p95가 6.4초(회차 범위 3.7~8.8초)로 락 순서 변경(1.6초)의 약 4배다. 락 순서 변경은 시도 자체를 없앤다.


## 3. 실험 2. 한글 오타 검색

**방법**: 검색 API는 외부 API와 변형 레시피 병합이 섞이므로 **정답률은 앱과 같은 쿼리를 MySQL·ES에 직접** 보냈다. 오타는 시드 고정으로 음식명 200개를 뽑아 6가지 유형으로 자동 생성하고, 자모 편집 거리(인접 교환 = 1, ES fuzziness와 같은 정의)가 정확히 1/2/3이 되게 했다. 대표 지표는 느슨 기준(상위 5개에 원래 음식명 포함)이고, 엄격 기준(원래 ID)은 참고용이다(`raw/exp2-score.md`).

### 방식 × 수정 횟수 정답률 (느슨 @5, 질의 시드 42·7·2026 범위)

> **주의**: 이 표의 "수정 횟수" 칸에는 오타 유형 구성이 다르게 섞여 있다. 특히 자모 2·3곳 칸에는 **음절 누락**(글자를 통째로 빠뜨림)이 들어 있는데, LIKE는 부분 문자열 매칭이라 음절 누락만 우연히 맞힌다. 공정한 비교는 바로 아래의 유형별 표를 본다.

| 방식 | 자모 1곳 | 자모 2곳 | 자모 3곳 (예상 실패 구간) |
|---|---|---|---|
| MySQL LIKE | 0% | 4.5~8.5% | 6.5~10% |
| MySQL FULLTEXT(ngram) | 0% | 4.5~8.5% | 7~10% |
| ES+Nori (boost 0) | 57.5~64.5% | 30.5~32.5% | 24~28.5% |
| **ES+Nori+Jamo (boost 3)** | **99.5~100%** | **93.5~96%** | 19.5~27% |

### 유형 × 수정 횟수 (느슨 @5, 질의 시드 42, 기존 5,000건)

| 자모 수정 | 유형 | n | LIKE | FULLTEXT | ES+Nori | ES+Nori+Jamo |
|---|---|---|---|---|---|---|
| 1곳 | 자모 수정만 | 200 | 0% | 0% | 58% | **100%** |
| 2곳 | 자모 수정만 | 172 | 0% | 0% | 28% | **95%** |
| 2곳 | 음절 누락 포함 | 28 | 32% | 32% | 54% | 86% |
| 3곳 | 자모 수정만 | 108 | 0% | 0% | 18% | 18% |
| 3곳 | 음절 누락 포함 | 92 | 22% | 21% | 41% | 38% |

- **LIKE·FULLTEXT가 맞힌 오타는 전부 음절 누락이 섞인 경우**이고, 자모만 고친 오타는 거리와 무관하게 **0%**다. 앞 표에서 LIKE가 자모 2곳에서 0%가 아닌 것은 그 칸에 음절 누락이 28건(14%) 들어 있어서다. 질의 시드 7·2026에서도 같은 구조다(자모 2곳 음절 누락 포함 LIKE 14/29, 17/29).
- ES+자모는 "자모만 고친" 오타 1~2곳을 95~100% 보정한다. 자모 3곳은 유형과 무관하게 18~38%로 떨어진다(예상 실패 구간).

- 데이터 시드 3종(5,000건)은 결과가 **완전히 같았고**, 50,000건도 차이가 0.5%p 이내였다(예: LIKE 정상 P@5 96.5% → 97.1%, ES 자모 3곳 27.0% → 26.5%). 생성기가 제목은 고정이고 점수·재료만 무작위라 오타 질의 결과에 거의 영향이 없다. 결과 편차는 질의 시드(42·7·2026) 쪽에서 나온다(위 표의 범위).
- 자모 3곳은 계획대로 실패 구간이다. 자모 1~2곳인데 틀린 질의는 시드마다 9~13건이고 원인은 짧은 음식명(자모 5 이하라 허용 편집 1), 음절 누락 포함, 기타 순이다(`raw/exp2/failures-*.json`).

### 기존 질의 세트 (k6/data/search-queries.json)

| 방식 | 정상 P@5 (34개) | 오타 P@5 (20개) | 오타 1위 정답 | 처음 보는 오타(holdout) 1위 |
|---|---|---|---|---|
| LIKE | 96.5% | 0.0% | 0 / 20 | 0 / 12 |
| FULLTEXT | 99.4% | 5.0% | 1 / 20 | 0 / 12 |
| ES+Nori (자모 전) | 97.6% | 36.0% | 8 / 20 | 4 / 12 |
| ES+Nori+Jamo | 98.2% | **97.0%** | **20 / 20** | **12 / 12** |

기존 문서(`k6/results/search-benchmark-results.md`)는 LIKE 정상 P@5 99.4%, ES+자모 97.6%, 오타 P@5 98.0%였다. 이번 값(LIKE 96.5%, ES+자모 98.2%, 오타 P@5 97.0%)과 다른 이유는 **측정 방식(기존은 검색 API 경유, 이번은 DB·ES 직접 질의)**과 데이터 시드 변동(기존 문서도 정상 P@5가 97.6~98.2% 범위에서 변동한다고 적었다) 때문으로 보인다. 오타 1위 정답률(20/20)은 그대로다.

50,000건에서도 오타 1위 20/20, holdout 12/12, 정상 P@5 98.2%(LIKE 97.1%)다.

### MySQL만으로 되는가: 자모로 분해한 제목 컬럼 + FULLTEXT(ngram)

"ES가 아니라 MySQL로도 오타 검색이 되는가"에 답하려고 로컬 DB에 `title_jamo` 컬럼(제목을 자모로 분해한 문자열)과 FULLTEXT(ngram) 인덱스를 추가해 **같은 오타 세트**(질의 시드 3종)와 기존 질의 세트로 DB에 직접 질의했다(5,000건, 인덱스 생성 0.8초, 앱 코드 변경 없음, 측정 후 컬럼·인덱스 삭제, `scripts/exp7_jamo_fulltext.py`).

| 방식 | 자모 1곳 | 자모 2곳 | 자모 3곳 | 정상 P@5 | 오타 1위 | 처음 보는 오타 |
|---|---|---|---|---|---|---|
| MySQL LIKE | 0% | 4.5~8.5% | 6.5~10% | 96.5% | 0/20 | 0/12 |
| FULLTEXT(제목) | 0% | 4.5~8.5% | 7~9.5% | 99.4% | 1/20 | 0/12 |
| **FULLTEXT(자모 컬럼)** | **89~93%** | **73.5~79%** | **56.5~70%** | 96.5% | **15/20** | **8/12** |
| ES+Nori+Jamo | 99.5~100% | 93.5~96% | 19.5~27% | 98.2% | 20/20 | 12/12 |

자모만 고친 오타(음절 누락 제외)로 한정하면 MySQL 자모 FULLTEXT는 1곳 89~93%, 2곳 71~75%, 3곳 54~66%이고, ES는 1곳 99.5~100%, 2곳 95~96%, 3곳 14~20%다.

- **MySQL만으로도 상당 부분 된다.** 컬럼 하나와 ngram 인덱스로 자모 1곳 오타의 약 90%, 기존 질의 세트 오타 1위 15/20을 맞힌다. "ES가 아니면 오타 보정이 불가능하다"는 주장은 성립하지 않는다.
- **ES는 자모 1~2곳에서 더 정확하다**(1곳 +7~11%p, 2곳 +17~22%p, 오타 1위 20/20 대 15/20, 처음 보는 오타 12/12 대 8/12).
- **자모 3곳에서는 MySQL ngram이 오히려 낫다**(54~70% 대 ES 14~27%). ES fuzziness는 편집 거리 2까지만 보정하지만, ngram은 일부 조각만 겹쳐도 후보가 되기 때문이다.
- 따라서 ES를 쓰는 근거는 "유일한 방법"이 아니라 **"1~2곳 정확도가 약 7~20%p 높고, 오타 1위·처음 보는 오타를 모두 맞힌다"**이다. 비용(ES 운영, 색인 동기화) 대비 이 차이가 가치가 있는지가 설계 판단이다.
- MySQL 질의는 클라이언트 오버헤드를 포함해 질의당 약 5ms였으나 앱·ES 지연과 직접 비교하지 않는다. 50,000건에서의 인덱스 크기·질의 시간은 측정하지 않았다.

### boost 민감도 (기존 5,000건, 질의 시드 42)

이 표는 boost 값을 다시 고르는 용도가 아니라 **3이 적당했는지 확인**하는 용도다.

| boost | 자모 1곳 | 자모 2곳 | 자모 3곳 | 정상 P@5 | 오타 1위 |
|---|---|---|---|---|---|
| 0 | 58.5% | 31.5% | 28.5% | 97.6% | 8/20 |
| 1 | 94.5% | 85.0% | 27.5% | 98.2% | 19/20 |
| 2 | 99.5% | 91.5% | 27.5% | 98.2% | 20/20 |

boost 3 이상은 결과가 같고, 2는 자모 2곳에서 약간 낮다(91.5% vs 93.5%). 정상 검색 P@5는 boost 1 이상에서 98.2%로 변하지 않는다. 3은 효과가 포화되는 지점의 안전한 값이었다.

### 지연 (검색 API 전체 응답, 외부 API 호출 포함, p95 median (min~max) ms)

| 데이터 | 동시 | MySQL LIKE | FULLTEXT | ES+Nori+Jamo |
|---|---|---|---|---|
| 5,000건 (n=4) | 10 | 87 (82~101) | 75 (72~78) | 98 (93~101) |
| 5,000건 (n=4) | 50 | 216 (207~278) | 161 (156~172) | 208 (201~212) |
| 50,000건 (n=2) | 10 | 280 (253~307) | 113 (107~119) | 175 (165~186) |
| 50,000건 (n=2) | 50 | **1170** (1037~1303) | 273 (256~291) | **258** (208~307) |

**외부 API를 stub으로 바꾼 재측정** (식품안전나라 호출을 호스트의 가짜 서버로 연결, 20ms 고정 지연, 코드 변경 없이 컨테이너 `extra_hosts`로 연결 / 5,000건 / 엔진 3종 × 10·50 VU × 1분 × 4회, 워밍업 제외 3회):

| 동시 | 엔진 | p95 median (min~max) ms | 1분 처리 요청 수 |
|---|---|---|---|
| 10 VU | MySQL LIKE | 79 (43~97) | 15,021 |
| 10 VU | FULLTEXT | 62 (49~66) | 18,694 |
| 10 VU | ES+Nori+Jamo | 95 (48~133) | 11,559 |
| 50 VU | MySQL LIKE | 189 (133~216) | 27,717 |
| 50 VU | FULLTEXT | 146 (141~150) | 34,757 |
| 50 VU | ES+Nori+Jamo | 201 (124~268) | 20,740 |

외부 호출을 없앤 뒤에도 **p95 회차 범위가 크게 겹쳐**(10 VU: LIKE 43~97, FULLTEXT 49~66, ES 48~133ms) p95의 순서를 단정하기 어렵다. 더 안정적인 지표는 **1분 처리 요청 수**이고 이 기준으로는 FULLTEXT(18,694) > LIKE(15,021) > ES(11,559)다(10 VU). ES는 FULLTEXT의 약 60% 처리량이다. 외부 API 호출이 엔진 간 차이를 가렸던 것은 아니다.

- **5,000건에서 ES는 LIKE보다 빠르지 않다.** 기존 k6 스크립트 대조도 LIKE p95 25.2ms, ES 26.7ms로 차이가 없다(기존 주장 "80.7 → 40.9ms, 49% 개선"은 재현되지 않았다).
- 50,000건 50 VU에서만 LIKE가 급격히 느려진다(1.17초 vs 0.26초).
- **FULLTEXT는 지연이 ES와 비슷하거나 더 빠르다.** 단 오타 보정은 못 한다(0~10%). 그래서 ES+Nori+Jamo의 근거는 속도가 아니라 오타 보정이다.
- **ES 엔진 자체 처리 시간(`took`, 질의 669개 median)**: 자모 절 없음(boost 0) 2ms, boost 1 11ms, boost 2·3 18ms, boost 5 17ms, boost 8 15ms. 자모 fuzzy 절이 엔진 시간을 약 2ms → 18ms로 늘린다. 다만 API 전체 응답(약 100ms)에 비하면 작다. (`_msearch` 순차 실행 기준, 부하 없음)

## 4. 실험 3. 추천 API 캐시

**측정한 것**: 지연(cold/warm × 1·50 VU, 5회 중 워밍업 제외 4회), 캐시 적중률(3회), 캐시 무효화 시간 50회, Redis 중단 시 응답 40건.
**하지 못한 것**: 알레르기·식단 변경에 따른 무효화, Redis 중단 시 실제로 얼마나 오래 매달리는지(클라이언트 타임아웃을 30초로 둬서 그 이상은 모름).

cold는 Redis를 비운 뒤 한 번도 요청하지 않은 사용자 1,000명이 한 번씩 요청해 만들었다. warm은 사용자 100명 × 추천 4종 키를 미리 채우고 Zipf(s = 1.0)로 1,000건을 요청했다. 모든 조건 실패 0%.

| 조건 | avg (ms) | p95 (ms) | p99 (ms) |
|---|---|---|---|
| cold, 1 VU | 16.5 (16.1~17.6) | 22.1 (20.9~23.1) | 27.2 (27.0~28.3) |
| warm, 1 VU | 2.6 (2.3~2.9) | 4.1 (3.3~4.7) | 5.4 (4.7~5.8) |
| cold, 50 VU | 82.4 (77.4~99.0) | 134.7 (124~170) | 190 (165~202) |
| warm, 50 VU | 20.9 (19.7~21.0) | 45.6 (41.7~61.1) | **148 (94~185, 흔들림)** |

- 캐시 적중 시 avg가 1 VU에서 약 6.3배, 50 VU에서 약 3.9배 빠르다.

### 추천 캐시 적중률 (Redis `INFO` keyspace_hits/misses, 3회, 1,000건씩) — 설계로 정해진 값, 성과 아님

앱에 Redis 캐시 통계가 꺼져 있어 Micrometer `cache.gets`에는 값이 없다. 매 조건 직전에 `CONFIG RESETSTAT`을 실행하고 추천 API만 호출했다.

| 조건 | 적중 | 미적중 | 적중률 |
|---|---|---|---|
| cold, 1 VU / 50 VU | 0 | 2,000 (3회 모두 동일) | **0%** |
| warm, 1 VU / 50 VU | 1,000 (3회 모두 동일) | 0 | **100%** |

cold의 미적중 2,000은 요청 1,000건이 추천 캐시와 그 안에서 조회하는 가족 알레르기 캐시를 각각 한 번씩 놓친 값이다(두 캐시 합산).

### 빈 캐시에서의 실제 적중률 추이 (Zipf 트래픽 7분)

위 0%/100%는 실험 설계값이라 성과가 아니다. 실제에 가까운 값은 **빈 캐시에서 Zipf(s = 1.0) 트래픽을 30 RPS로 7분(12,600건, 사용자 1,000명 × 추천 4종 = 4,000개 키) 흘리고** 10초 창마다 적중률을 읽어 구했다(드롭 0, 실패 0, p95 32ms). Redis `INFO`의 조회 수 L에서 요청 수 R을 빼면 추천 캐시 미적중 수가 나오므로(미적중 1건당 알레르기 캐시 조회가 1회 더 생긴다) 창 안의 적중률은 1 − (L − R)/R로 계산했다.

| 구간 | 평균 적중률 (min~max) |
|---|---|
| 0~60초 | 51% (26~63%, 첫 10초 26%) |
| 60~180초 | 73% (64~79%) |
| 180~300초 | 81% (77~86%) |
| 300~420초 | 74% (68~79%, 마지막 부분 창 제외) |

- 약 3분 만에 70%대, 최고 81%에 도달한다.
- 5분 시점부터 처음 채워진 키의 TTL(5분)이 만료돼 적중률이 70%대로 내려가는 톱니 모양이 나타난다. TTL을 늘리면 적중률은 오르지만 무효화 지연과 맞바꾸게 된다.
- 요청 속도를 R = rate × 10초로 가정한 추정값이고(드롭 0으로 확인), 마지막 창은 부하가 끝난 뒤의 부분 창이라 제외했다.

### Redis 중단 시 응답

Redis 컨테이너를 멈춘 상태에서 추천 API를 40회 호출했다: **40건 모두 응답 없이 30초 타임아웃**(median 30.0초). 코드를 확인하니 캐시 오류 처리기(`CacheErrorHandler`)와 Redis 명령 타임아웃 설정이 없어 DB로 우회하지 못한다. 클라이언트 타임아웃을 150초로 늘려 다시 재면 60.1초 뒤 500이 반환된다(아래 수정 실험의 기준선). 캐시 장애가 서비스 전체 장애로 번지는 설계 약점이다.

### Redis 장애 격리 수정 실험 (부하 중 Redis 30초 중단)

**기준선**: 수정 전 코드(v3)에서 Redis를 멈추고 추천 5건을 동시에 보냈다(클라이언트 타임아웃 150초). 5건 모두 **정확히 60.1초 뒤 HTTP 500**이었다. 앞서 "30초 타임아웃"이라고만 말한 것이 이제 "요청이 스레드를 60초 붙잡다 실패"로 확정됐다(Lettuce 명령 타임아웃 기본값 60초와 일치).

**장애 주입**: 4개 API 혼합(검색 40%, 추천 30%, 상세 15%, 식단 15%) 60 RPS 부하 중 약 30초 동안 Redis 컨테이너를 중단하고 복구했다. 변형마다 3회, 클라이언트 타임아웃 5초, 단계(장애 전·중·후)와 API별 실패율을 집계했다(`scripts/exp6_redis.py`, 결과 `results.csv`의 `exp6`). 수정은 앱 코드를 바꾼 별도 worktree 이미지이고 `fix/#20-redis-failure-isolation` 브랜치에 있다.

| 변형 | Redis 중단 중 실패율 (검색 / 추천 / 상세 / 식단) | 전체 | 복구 후 전체 | 복구 시간 |
|---|---|---|---|---|
| 수정 전 (v3) | 99.7~100% / 99.6~100% / 85~93% / 84~89% | **95.0~97.2%** | 0.0~9.2% | 0~1초 |
| 1차: `CacheErrorHandler`만 + Redis 타임아웃 200ms | 100% / 100% / 0% / 0% | 68.8~71.6% | 10.9~12.1% | 6~7초 |
| **2차: 캐시 래퍼(`FailureTolerantCache`) + Redis 타임아웃 200ms** | 0~0.4% / 0% / 0% / 0% | **0.0~0.2%** | **0.0%** | **0초** |

- **수정 전에는 장애가 서비스 전체로 번진다.** Redis와 무관한 상세·식단도 84~93%가 실패한다(추천이 스레드를 60초씩 붙잡아 Tomcat 스레드가 고갈된 것으로 해석한다. 스레드 수를 직접 재지는 않았다).
- **1차 수정은 전파는 막았지만 충분하지 않았다.** 상세·식단은 0%로 살아났으나 검색·추천은 100% 500이었다. 캐시 매니저가 `transactionAware`라서 저장·삭제가 **트랜잭션 커밋 뒤에** 실행되는데, 이때 던져진 예외는 `CacheErrorHandler`를 거치지 않고 요청으로 올라가기 때문이다(원인은 코드 구조와 결과로 추정, 로그로 스택을 확인하지는 않았다). 복구 후에도 11~12%가 실패했다.
- **2차 수정**은 오류 처리를 트랜잭션 데코레이터 안쪽(실제 `RedisCache` 바로 바깥)에 두어 조회·저장·삭제 오류를 모두 삼키고 원본(DB)으로 우회한다. 장애 중 실패 0~0.2%, 복구 즉시 정상이다. 단위 테스트 4개(`FailureTolerantCacheTest`)가 통과했다.
- **비용**: 2차 수정에서 장애 중 **성공한 요청의 p95는 856~1,637ms**(장애 전 25~28ms)다. 캐시를 못 쓰고 DB로 우회하는 데다 Redis 연결 시도가 200ms 타임아웃을 소모하기 때문이다. "장애가 나도 응답은 하지만 느려진다"가 정확한 표현이고, "영향 없음"이 아니다.
- **다른 Redis 사용처는 보호되지 않았다.** 알림 SSE 발행(`RedisTemplate.convertAndSend`)과 Pub/Sub 구독은 이 수정 범위 밖이라 장애 중 동작을 측정하지 않았다. Kafka 소비자의 캐시 삭제도 확인하지 않았다.
- 1차 수정은 팀에 제안하지 않고 폐기했다. 결과는 기록용으로 남긴다(패치: `scripts/redis-variants/`).

### 캐시 무효화 (찜 추가 → 추천 캐시 갱신)

| 지표 | 값 |
|---|---|
| 시도 / 성공 / 쓰기 전 옛 값이 캐시돼 있었던 경우 | 50 / 50 / 50 |
| 새 값이 보일 때까지 | p50 34ms, p95 74ms, 최대 87ms |
| 10초 안에 새 값이 안 보인 경우(지속 stale) | **0건** |
| 옛 값을 돌려준 읽기 | 50회 시도 중 8회(시도당 최대 1회) |

- 동시에 10ms 간격으로 같은 캐시를 읽었는데도 영구 stale이 한 번도 없었다(`afterCommit`에서 Kafka 발행).
- **찜 추가 경로만** 측정했다. 알레르기·식단 변경 경로는 측정하지 않았다.

## 5. 실험 4. 처리량 (재설계)

### 5.1 왜 다시 했나
1차 측정(부록 A)은 포화 구간 실패 187만 건이 **전부 연결 거부·강제 종료이고 5xx가 0건**이었다. 요청이 Windows의 Docker Desktop 포트 포워딩(`127.0.0.1:8080`)을 지나므로 앱이 아니라 로컬 네트워크 계층의 한계를 쟀을 가능성이 컸다. 요청률 단계(200→400→600)가 2배씩 뛰어 결과가 한 단계 차이로 출렁였고, 실패 요청이 0ms로 섞여 p95가 낮게 나왔으며, 식단 API 404(5~16%)와 첫 회차 워밍업도 섞여 있었다. 그래서 이 1차 결론("튜닝 효과 불분명")은 폐기하고 아래와 같이 다시 설계했다.

### 5.2 설계
| 이전 문제 | 이번 수정 |
|---|---|
| 포트 포워딩 경로 | **k6를 Docker 네트워크 안 컨테이너로 실행**(`grafana/k6` v2.4.0, `app:8080` 직접 요청, 컨테이너 CPU 3.5코어 제한) |
| 단계가 2배씩 뜀 | **300~600 RPS를 50 단위**, 단계당 60초 |
| 실패가 p95에 0ms로 섞임 | **성공(200) 응답만으로 p95 계산**(`expected_response:true`) |
| 404 | 가족방 1~100에 이번 주 CONFIRMED 식단을 미리 넣어 **404 0건**(전 단계 확인) |
| 워밍업 | 매 회차 컨테이너를 새로 띄우고 200 RPS 30초 예열, **1회차는 집계 제외**(2~4회차 3회 집계), 설정 순서를 라운드마다 회전 |
| 외부 API 변동 | 호스트의 stub(20ms 고정 지연)으로 연결 |

설정은 3종: 기본값(Hikari 10, Tomcat 200), Hikari만 50, 전체 튜닝(Hikari 50 + Tomcat 500 + max_connections 200). SLO = 성공 응답 p95 ≤ 1,000ms, 비200 ≤ 1%, 드롭 ≤ 1%. 앱 6, MySQL 4, Redis 1, ES 2, Kafka 1, ZooKeeper 0.5, k6 3.5코어(합 18). 회차 중 절전이 걸쳤던 `default` 3회차는 무효 처리하고 다시 쟀다(`raw/exp4b/invalid-system-sleep/`).

### 5.4 해석
1. **기본값은 약 550 RPS까지 SLO를 지키고 600에서 무너진다**(0/3, p95 1.5초). 그 시점에 Hikari 풀 10개가 모두 쓰이고 Tomcat 스레드가 커넥션을 기다린다(대기 198). 앱 CPU는 445%로 제한(600%)에 못 미쳐 **병목은 풀이다.**
2. **전체 튜닝은 600 RPS에서 3/3 통과하고 p95가 590ms(359~629)**로 기본값(1,117~2,423ms)과 범위가 겹치지 않는다. 이때 앱 CPU가 629%로 제한에 닿아 병목이 **풀에서 CPU로 이동**했다. 다만 600이 측정한 최고 단계라서 **전체 튜닝의 상한은 모른다**(600 이상은 측정하지 않았다).
3. **Hikari만 키운 설정은 기본값보다 나아지지 않았다**(통과율 56%, 회차 간 변동 큼: 최대 350~600). 풀만으로는 부족하고 Tomcat 스레드·대기열 확대가 함께 필요했을 가능성이 있다. **Tomcat만 바꾼 설정은 이번 재설계에서 재지 않았으므로 항목별 기여도는 단정할 수 없다.**
4. 같은 설정도 회차마다 달라진다(전체 튜닝 350~450 구간에서 가끔 실패). 3회 표본의 한계라서 "개선 폭"을 퍼센트로 말하지 않는다. 600 RPS처럼 범위가 겹치지 않는 지점에서만 차이를 주장한다.
5. k6 컨테이너 CPU가 133~202%로 제한(350%)에 못 미쳐 **부하 생성기가 병목은 아니었다.**

### 5.5 커넥션 점유 시간 (추가 측정, 풀 포화의 원인)

Hikari 풀이 왜 포화하는지, 풀 크기 문제인지 **누가 커넥션을 오래 쥐는지**의 문제인지 보려고 Hikari 타이머(`hikaricp.connections.usage` = 빌려 쓴 시간, `acquire` = 빌리려고 기다린 시간)를 부하 전후로 읽었다. 이 지표는 풀 단위라 API별 태그가 없어서 **API마다 단독으로 100 RPS를 60초씩** 걸었다(앱: v4, 원래 compose 설정 Hikari 50, 외부 API stub, 설정당 3회 중 1회차 워밍업 제외 2회, `scripts/exp5_connhold.py`). 검색은 키워드마다 숫자를 붙여 외부 API 캐시를 항상 미적중시켰다.

| API | 처리 요청(60초, 목표 6,000) | 요청당 커넥션 빌림 | 빌린 뒤 점유 시간/건 | **빌리려 기다린 시간/건** | 요청 평균 → p95 |
|---|---|---|---|---|---|
| 추천(캐시 적중) | 6,001 | 0.03 | 8ms | 0 | 2 → 3ms |
| 상세 | 6,001 | 1.02 | 3ms | 0 | 6 → 8ms |
| 식단 | 6,001 | 1.02 | 5ms | 0 | 7 → 10ms |
| **검색 (외부 stub 20ms)** | 5,310 | **2.02** | **225ms** (181~269) | **957ms** (404~1,509) | **2,458 → 12,039ms** |
| 검색 (외부 stub 300ms) | 5,442 | 2.02 | 261ms (251~271) | 1,166ms (1,146~1,185) | 2,881 → 8,319ms |

- **풀 포화의 주범은 검색이다.** 검색은 요청당 커넥션을 2번 빌리고 한 번에 약 230~260ms를 쥐며 빌리려 기다린 시간이 건당 약 1초다. 요청당 대기가 약 2초라서 **검색 요청 시간(평균 2.5~2.9초)의 대부분이 커넥션 대기**다. 다른 API는 대기가 0이다.
- **Little의 법칙으로도 맞는다**: 처리량 약 88건/초 × 요청당 점유 약 0.5초 ≈ 44개의 커넥션이 평균적으로 쓰여 풀 크기(50)에 닿는다. 100 RPS 중 목표 대비 약 11%(검색)가 처리되지 못했다.
- **외부 API 호출 동안 커넥션을 쥔다는 가설은 지지되지 않았다.** 외부 API 지연을 20ms에서 300ms로 늘렸는데 요청당 점유 시간은 454 → 526ms로 거의 그대로이고(범위가 겹침) 요청 평균만 늘었다. 지연이 커넥션 점유에 포함되지 않으니 외부 호출 중에는 커넥션이 풀려 있다고 본다. `open-in-view`는 켜져 있다(앱 기동 로그 경고로 확인).
- **한계**: 점유 시간 225~261ms가 이 쿼리의 고유 시간인지, 포화 때문에 늘어난 것인지는 이 측정만으로는 구분하지 못했다(저부하 재측정 필요). 검색이 요청당 커넥션을 2번 빌리는 이유(한 요청 안의 두 트랜잭션 또는 두 번의 조회)도 코드로 따로 확인해야 한다.

### 5.6 한계
- 600 RPS 상한에서 끊어 튜닝 설정의 한계점을 못 찾았다. 600 이상 단계가 필요하다.
- Tomcat만, max_connections만 바꾼 설정은 재설계에서 재지 않았다(1차 측정에서는 Tomcat만 바꿔도 변동 폭이 컸으나 그 측정은 폐기).
- 앱·DB·k6가 같은 노트북에서 돈다(k6는 컨테이너 CPU 제한으로 격리). 회차 3회, 단계당 60초.
- 커넥션 점유 시간은 5.5절에서 API별 단독 부하로 측정했다. 풀 포화의 원인은 풀 크기만이 아니라 검색 API(요청당 커넥션 2번, 건당 약 230ms 점유, 대기 약 1초)다.

## 7. 슬라이드 사용 가이드

**써도 되는 수치** (5회 이상 측정, 원본 보관)
- "INSERT 후 UPDATE 구조에서 100명 동시 리뷰 중 **94건(92~95)이 교착으로 실패**, UPDATE를 먼저 실행하도록 바꾸면 0건" (로컬, 5회)
- "10명 동시부터 교착이 시작되고, 리뷰·변형 리뷰·찜·변형 찜 4개 경로 모두 같은 구조로 재현"
- "재검증 중 평균 별점이 절반으로 저장되는 버그를 발견해 수정" (v3 100/100 불일치 → v4 0/100)
- "오타 정답률: 자모만 고친 오타 1~2곳에서 LIKE/FULLTEXT 0% → ES+자모 필드 95~100%"(음절 누락이 섞이면 LIKE도 22~32% 맞힘), "기존 질의 세트 오타 1위 20/20, 처음 보는 오타 12/12"
- "평균 별점 반올림 누적 오차: 리뷰 2,000건 동시에 레시피 20개 중 12~13개가 어긋남 → 점수 합계(`score_sum`) 저장으로 0개, 오차 0.0" (실험용 변형, 3세트 6,000건, 메인 코드에는 미반영)

- "교착 해결 방법 비교: 같은 트랜잭션 안 재시도는 구조상 불가능(rollback-only, 262회 모두 확인), 밖에서 10회 지수 백오프 재시도는 98/100이지만 p95 6.4초·교착 시도 294건, **락 순서 변경은 100/100·p95 1.6초·교착 0건**" (새로 구현한 비교임을 명시)
- "추천 캐시: 적중 시 응답 약 4~6배 빠름, 빈 캐시에서 Zipf 트래픽을 흘리면 약 3분 만에 적중률 70%대, 최고 81%" (**조건**: 사용자 1,000명, 키 4,000개, 30 RPS, TTL 5분, Zipf s = 1.0, 로컬). **적중률 0% / 100%는 성과가 아니다**(실험 설계값)

**조건을 붙여야 하는 수치**
- 리뷰 100명 동시 p95 1.9초: "같은 레시피에 100명이 몰리는 극단 조건, 직렬화 대가"
- 50,000건에서 LIKE p95 1.17초 vs ES 0.26초: "50 VU, 외부 API 호출 포함, n=2"
- 캐시 효과 약 4~6배: "로컬, 추천 4종, avg 기준 상대 비교"
- 캐시 무효화 p95 74ms, 영구 stale 0: "찜 추가 경로만"
- 검색 지연(외부 API stub, 5,000건): p95는 범위가 겹쳐 순서를 단정하지 말고 "**1분 처리 요청 수 FULLTEXT 18,694 > LIKE 15,021 > ES 11,559(10 VU)**, ES는 FULLTEXT의 약 60%"처럼 처리량으로 말하고 ES가 느리다는 사실을 함께 적을 것(ES의 이유는 오타 보정)
- FOR UPDATE 대비 UPDATE 먼저: "**경합이 있을 때 p95 약 14~16% 낮음**"(같은 코드에서 락 순서만 바꾼 비교, 5회). 앞서 쓴 "7~27%"는 다른 커밋 간 비교라 철회했다. 큰 개선으로 포장하지 말 것(기존 "4.65 → 0.92초"는 재현 안 됨)
- 처리량: "**기본 설정은 약 550 RPS까지, 전체 튜닝은 600 RPS에서도 p95 1초 이내**"(재설계, 로컬, 회차 3회). "기본 설정 대비" 표현만 쓰고 600 RPS 이상은 측정하지 못했다고 적을 것. Hikari 풀만 키운 설정은 효과가 없었다는 점도 함께
- Redis 장애 격리: "Redis 30초 중단 시 전체 요청 **95~97%가 실패**(Redis와 무관한 상세·식단도 84~93%) → 캐시 오류를 삼키고 DB로 우회하도록 고치자 **0~0.2%**, 복구 즉시 정상"(로컬, 3회, 60 RPS 혼합 부하). **조건**: Redis 타임아웃을 200ms로 줄이는 설정 필요, 장애 중 성공 응답 p95는 0.9~1.6초로 느려짐, 알림 Pub/Sub 등 다른 Redis 사용처는 미검증, 수정은 별도 브랜치(PR 전)
- 커넥션 점유: "검색이 요청당 커넥션을 2번 빌리고 건당 약 230ms 쥐어 풀 대기 약 1초가 발생, 추천·상세·식단은 대기 0"(100 RPS 단독, 원인 분해는 저부하 재측정 필요)
- MySQL 자모 컬럼 + FULLTEXT: "컬럼 하나로 자모 1곳 오타 89~93% 정답, ES는 99.5~100%" (5,000건, DB 직접 질의)

**쓰면 안 되는 수치**
- "85건 → 0건", "15 → 100건", "58/100", "찜 p95 4.65 → 0.92초", "ES 도입으로 p95 49% 개선", "처리량 733 → 1,012 RPS(+38%)", "3000 VU p95 3.18초", "에러 0%"
- "튜닝으로 처리량이 38% 늘었다" 같은 퍼센트(기존 VU 방식 RPS는 실패 요청 때문에 부풀려지고 재현되지 않음), "Hikari 풀만 키우면 좋아진다"(효과 없었음)

## 8. 한계

- **k6와 앱이 같은 노트북(18 논리 CPU, 31.6GB)에서 실행**됐다. 실험 4는 서버 컨테이너 CPU를 제한하고 k6용 코어를 남겼지만 완전한 분리는 아니다. 절대 수치는 이 머신의 값이다.
- **측정 환경 사고**: 2026-11-19 20:25~21:15 노트북 절전(Modern Standby)으로 실험 4 `maxconn` 1회차가 무효가 되어 재측정했다(원본은 `raw/exp4/invalid-system-sleep/`). 22:34에 덮개 1초 닫힘이 있었으나 해당 회차는 유효로 확인했다. 메모리 부족으로 백그라운드 실행이 한 번 중단돼 이어서 실행했고, 이 시점의 기존 스크립트 대조 1차 결과는 무효 처리했다(`raw/exp2/invalid-legacy-first-try/`). 재설계 측정에서는 11-20 15:03~19:13 절전이 `default` 3회차에 걸려 무효 처리 후 재측정했다.
- **처리량 1차 측정(포트 포워딩 경로)은 폐기했다.** 실패가 전부 연결 거부·강제 종료였고 k6를 Docker 네트워크 안에서 돌리자 사라졌다. 재설계 측정도 앱·DB·k6가 같은 노트북에서 돌고(k6는 컨테이너 CPU 3.5코어 제한, 사용 133~202%), 회차 3회, 단계당 60초라는 한계가 있다.
- 표본: 실험 1은 조건당 4회(워밍업 제외), 50,000건 검색 지연은 2회, 실험 4 재설계는 설정당 3회(1회차 워밍업 제외), 기존 VU 방식 재현(부록 A)은 설정당 1~2회다.
- v4는 다른 변형과 번갈아 실행하지 않아 지연 비교에서 제외했다.
- 처음 측정한 검색 지연(5,000건·50,000건)은 외부 식품안전나라 API(더미 키) 호출이 섞인 전체 응답 시간이다. 이후 외부 호출을 호스트의 stub(20ms 고정 지연, 컨테이너 `extra_hosts` 연결)으로 바꿔 5,000건만 다시 쟀고, 50,000건은 stub으로 다시 재지 않았다. ES 엔진 시간(`took`)은 부하 없이 순차 측정한 값이다.
- 락 순서 비교의 찜 경로는 원본 레시피 경로만 모드를 적용했다(변형 레시피 경로는 UPDATE 먼저 그대로). 점수 합계 변형은 리뷰 경로만 검증했다.
- 캐시 적중률 시간 추이는 요청 속도를 고정(30 RPS)해 창당 요청 수를 추정한 값이다(드롭 0으로 확인).
- **측정 환경 사고(추가)**: 메모리 부족으로 백그라운드 체인이 중단된 뒤 하위 프로세스가 살아 새 체인과 겹쳐 실행된 것을 발견해 겹친 4회차 2건을 폐기하고 다시 쟀다(`raw/exp2/discarded-overlap/`). 레시피 ID 풀 소진으로 락 순서 비교 1차 실행도 중단돼 DB를 기준 시드로 되돌린 뒤 다시 쟀다(`raw/p2-aborted-id-pool/`).
- 자모 + FULLTEXT 비교는 5,000건, DB 직접 질의로만 측정했다(앱을 거치는 지연, 50,000건은 미측정). 오타는 자동 생성이라 실제 사용자 오타 분포와 다를 수 있다. 데이터 시드 편차는 생성기 특성상 확인되지 않았다.
- 시드 데이터는 Math.random 기반 생성기라 원래 시드가 고정돼 있지 않다. `scripts/exp2/seeded-random.cjs`로 감싸 재현했다.
- 추천 캐시 경로 중 알레르기·식단 변경에 따른 무효화는 측정하지 않았다. Redis 중단 시 응답은 부하 중 장애 주입으로 확인했다(4장 수정 실험: 기준선에서 60.1초 뒤 500)..
- 재시도 비교는 새로 구현한 코드이고 대기 방식(고정 10~50ms, 지수 백오프) 등 구현 세부가 옛 코드와 다를 수 있다. 결과가 이 설계에 민감하므로 다른 백오프(예: 더 긴 대기, 지터 크기)에서는 수치가 달라질 수 있다.
- 추천 적중률은 Redis `INFO` 기준이라 추천 캐시와 가족 알레르기 캐시 조회가 합산돼 있고, 시간 추이는 "미적중 1건당 알레르기 조회 1회"라는 가정으로 추정한 값이다. 캐시별 통계를 직접 쓰려면 `RedisCacheManager`에 통계를 켜야 하는데, 이 앱은 `RedisCacheManager.builder(...)`로 직접 구성해서 Spring Boot의 `spring.cache.redis.enable-statistics` 설정만으로는 켜지지 않을 가능성이 크다(코드에서 `.enableStatistics()` 호출이 필요할 수 있고, 검증하지 않았다).
- CPU 제한 없는 처리량 재현은 설정마다 2회, k6와 앱이 CPU를 경쟁한다.
- 찜 기반 추천 정렬에서 `.reversed()`가 연속 호출돼 동점 시 평균 별점이 오름차순이 되는 코드 문제를 발견했으나 범위 밖이라 고치지 않았다.

## 부록 A. 폐기한 측정: 실험 4 1차 (Docker 포트 포워딩 경로)

> **이 부록의 결과는 포트 포워딩 경로를 거친 측정이라 결론에 쓰지 않는다.** 재설계 결과(5절)와 충돌하는 부분은 5절이 맞다.

### (옛 5절) 실험 4. 처리량

**조건**: 앱·MySQL·Redis에 CPU 제한(앱 6, MySQL 4, Redis 1, ES 2, Kafka 1, ZK 0.5 → 서버 측 14.5개), k6용 약 3.5개를 남겼다(`scripts/exp4/cpus.yml`). `ramping`이 아닌 `constant-arrival-rate`로 100·200·400·600·800·1000·1200·1500 RPS를 단계당 60초씩 올렸다. 성공은 HTTP 200만 인정하고 404(식단 없음, 약 5~16%)는 따로 센다. **"튜닝 전"은 원래 설정이 기록에 없어 "기본값"(Hikari 10, Tomcat 200, accept 100, max_connections 151)으로 부른다.**
SLO = p95 1초 이하 + 5xx·연결실패 1% 이하 + 드롭 1% 이하. 설정마다 3회(번갈아 순서 회전, 3라운드 일부와 무효 회차 재측정은 중단 후 이어서 실행).

> **실패의 정체 (재검토에서 확인)**: 15회 전체에서 **5xx는 0건**이었고, 실패 187만 건은 모두 연결 수준 오류였다 — `127.0.0.1:8080` 연결 거부("actively refused")와 원격 강제 종료("forcibly closed"). 이 주소는 Windows 쪽에서 Docker Desktop이 컨테이너로 포트를 넘겨주는 지점이다. 따라서 포화 구간의 실패 상당 부분이 **앱이 아니라 로컬 테스트 환경의 네트워크 계층(포트 포워딩 또는 연결 대기열)**에서 생겼을 가능성이 크다. 확정하려면 k6를 같은 Docker 네트워크 안에서 실행해 비교해야 한다(미실시). 또 실패한 요청은 응답 시간이 0에 가깝게 기록되므로, 실패가 있는 단계의 p95는 실제보다 낮게 나온다. SLO 최대 RPS는 실패율 1% 이하인 단계만 통과로 치므로 이 영향을 받지 않는다.

### SLO를 지키는 최대 RPS

|---|---|---|---|---|---|

### 단계별 p95 (median, min~max) — **흔들린 항목**

| 설정 | 200 RPS | 400 RPS | 600 RPS (연결 실패율, 5xx 0) |
|---|---|---|---|
| 기본값 | 21 (21~304) | 1489 (162~4347) | 2949 (20.8%) |
| Hikari만 | 23 (22~297) | 532 (48~1920) | 4039 (8.8%) |
| max_connections만 | 68 (24~210) | 2224 (51~2592) | 3598 (20.2%) |
| Tomcat만 | 21 (21~26) | **274 (67~2220)** | 3097 (0.0%) |
| 전체 튜닝 | 22 (22~28) | **290 (281~1369)** | 6115 (31.4%) |

- 200 RPS에서는 모든 설정이 같다. **400 RPS에서 Tomcat만/전체 튜닝의 p95 median이 기본값보다 낮지만(274·290 vs 1489ms) 회차 간 범위가 크게 겹쳐** 설정 효과로 단정하기 어렵다. 600 RPS에서는 모든 설정이 SLO(p95 1초)를 넘고 대부분 연결 실패가 생긴다.
- 요청률 단계(…200, 400, 600)가 듬성해 한 단계 차이가 곧 2배라 SLO 최대 RPS가 크게 출렁인다.

| 조건 | 설정 | 평균 RPS(실패 포함) | 실패율 | 성공(2xx) 환산 RPS | p95 (초) |

- 제한 없는 조건에서도 기존 "733 → 1,012 RPS(+38%)", "에러 0%", "p95 3.99 → 3.18초"는 **재현되지 않았다.** 평균 RPS는 기본값과 튜닝이 같은 수준(848 vs 818)이다.
- 다만 **성공 환산 RPS는 튜닝에서 약 13% 높고(342 → 387) 실패율이 낮다**(59~60% → 49~56%). 효과는 있어도 크지 않은 정도로 보이며, 2회 표본이라 단정하지 않는다.
- 실패율이 50~70%인 상태에서는 실패 요청이 빨리 끝나 VU가 곧바로 다음 요청을 보내므로 **RPS가 부풀려진다.** 이 실패도 5xx가 아니라 연결 거부·강제 종료다(예: CPU 제한 없는 기본값 1회차 연결 거부 103,100건). 성공 응답만 본 p95는 5.5~5.9초로 전체 p95(5.2~5.6초)보다 높다. 기존 스크립트는 404를 성공으로 처리했고(checks) 유저 1명만 써서 추천이 항상 캐시 적중이었다. 이번 환경(CPU 제한, k6 같은 머신)에서는 기존 주장 "733 → 1,012 RPS(+38%)"가 재현되지 않았다.

- k6 자체도 최대 약 6코어(570~660%)를 쓴다. 호스트(18 논리 CPU)를 포화시키지는 않았지만 부하 생성기와 서버가 같은 머신이라는 한계는 남는다.
