# 포트폴리오 수치를 다시 검증한 기록 — 문제, 전략, 과정, 결과

> URISIK 백엔드 · 이슈 #18 · 2026-11-19 ~ 11-20
> 수치의 출처는 `REPORT.md`(정리된 결과), `results.csv`(지표 전체), `raw/`(원본)이다. 환경은 `env.md`.

## 요약

자소서와 면접에 쓰던 성능·정합성 수치의 원본을 찾으려다, 근거가 남아 있지 않거나 조건이 섞인 수치가 많다는 것을 알게 됐다. 그래서 "원본을 요구받아도 보여줄 수 있는 수치"를 목표로 과거 코드를 그대로 재현해 다시 측정했다.

- **유지·강화된 것**: 동시 리뷰 교착 해결(100명 중 약 94건 실패 → 0건). 재시도와 선잠금을 같은 조건에서 비교해, 락 순서 변경이 정합성은 같고 지연은 가장 낫다는 근거를 새로 얻었다.
- **재현되지 않은 것**: 85건, 58/100, 찜 p95 4.65→0.92초, ES 49% 개선, 처리량 733→1,012 RPS.
- **새로 발견한 것**: 평균 별점이 절반으로 저장되는 버그(수정함), Redis 장애 시 응답이 멈추는 약점, 그리고 측정 도구 자체가 결과를 왜곡하던 문제 두 가지.

## 1. 문제: 왜 다시 측정했나

면접 예상 질문("교착 상태를 어떻게 확인했나요?", "p95는 어떤 조건에서 쟀나요?")에 답하려고 커밋 기록과 결과 파일을 뒤졌다. 근거가 약한 수치가 세 종류 나왔다.

| 종류 | 예 | 문제 |
|---|---|---|
| 원본이 없는 수치 | "100명 중 85건 교착", "재시도 58/100", "FOR UPDATE p95 5.2초" | 개인 필기에만 있고 저장소에 로그가 없음 |
| 조건이 섞인 수치 | 찜 p95 4.65초 → 0.92초 | 토큰 발급 요청까지 p95에 포함, Before·FOR UPDATE는 1회 측정 |
| 이야기와 측정이 어긋난 수치 | 자소서는 "리뷰", 교착 로그는 "찜" 테스트 | 리뷰 쪽 수정 전 측정 기록이 없음 |

그래서 목표를 이렇게 정했다.
1. **원본을 남긴다.** 필기에만 남았던 실수를 반복하지 않는다.
2. **결과가 기대와 달라도 그대로 기록한다.** 기존 주장은 "일치 / 불일치 / 재현 불가"로 판정한다.

## 2. 전략: 실험을 믿을 수 있게 만든 설계 원칙

| 원칙 | 이유 | 실제로 막아 준 문제 |
|---|---|---|
| 과거 코드를 커밋 그대로 빌드해 비교(`git worktree`), 메인 코드 수정 금지 | "실험용으로 고친 코드"가 아니라 실제로 있었던 코드끼리 비교해야 한다 | 비교 대상이 흔들리지 않음 |
| **수정 전(v0)을 "원자적 UPDATE를 적용한 뒤"로 정확히 고름** | 원래 이야기는 `reviewCount++`의 Lost Update → 원자적 UPDATE → 그 뒤 교착 순서다. v0가 `++` 시절이면 두 문제가 섞인다 | `0e223cf`: `SET review_count = review_count + 1`이면서 INSERT가 먼저인 커밋 |
| 변형을 라운드마다 번갈아 실행 | 한 변형을 몰아서 돌리면 발열·백그라운드 작업이 한쪽에만 몰린다 | 처음 순차 실행한 데이터는 참고용으로만 보관 |
| 조건마다 5회, 1회차는 워밍업으로 제외, median과 min~max | 운 좋은 1회를 수치로 쓰지 않기 위해 | 앱 재기동 직후 첫 회차가 실제로 더 느렸다(예: cold 50 VU avg 118ms vs 이후 77~99ms) |
| **서로 다른 출처의 지표를 대조** | 지표 하나만 믿으면 도구 오류를 못 잡는다 | InnoDB 교착 카운터와 앱 로그 1213 건수를 함께 기록해 로그 집계 버그를 찾았다 |
| 정합성은 SQL로 직접 확인 | API 응답이 아니라 DB에 실제로 저장된 값이 기준이다 | 이 검사로 평균 별점 버그를 찾았다 |
| 대상 API만 따로 측정(k6 태그) | 지난번 p95에는 토큰 발급 요청이 섞여 있었다 | 리뷰·찜 API만의 p50/p95/p99 |
| 원본 보관 + 무효 처리 규칙 | 이상한 회차를 조용히 버리지 않고, 사유를 남긴 채 격리 | `invalid-*` 폴더마다 README로 사유 기록 |

## 3. 과정: 실험별로 무엇을 묻고, 무엇을 발견했나

### 3.1 실험 1 — 동시 리뷰의 교착은 진짜였나

**질문**: INSERT 후 UPDATE 구조에서 정말 교착이 나는가? 해결안(UPDATE 먼저)은 정말 0건인가?

**설계**
- 변형 4개를 비교했다: v0(INSERT → UPDATE), v1(SELECT FOR UPDATE), v3(UPDATE 먼저, 현재), v4(나중에 추가).
- 시나리오는 질문 하나씩에 대응한다: 같은 레시피 100명(A), 서로 다른 레시피 100개(B, 회귀 확인), 10~200명 확장(C, 시작 지점), 리뷰·찜 × 원본·변형 4개 경로(D), 기존 찜 측정과 같은 조건(E).

**측정하다 발견한 측정 도구의 결함 두 가지**
1. **같은 사용자가 두 번 요청하고 있었다.** 교착이 없는 버전인데도 99/100, 199/200이 나왔다. k6 `shared-iterations`는 VU가 요청을 1회씩 가져간다는 보장이 없어서, 빠른 VU가 두 번 요청하면 같은 사용자가 같은 레시피에 중복 리뷰를 쓴다(409). 11월 5일 기록의 "99건 + 중복 1건"도 같은 원인으로 보인다. VU당 정확히 1회인 `per-vu-iterations`로 바꾸고 처음부터 다시 측정했다.
2. **앱 로그의 교착 건수가 회차마다 누적되고 있었다.** `docker logs --since`에 시간대 표기 없는 UTC 시각을 넘겨, Docker가 이를 한국 시간으로 해석해 9시간 전부터 읽고 있었다. InnoDB 카운터 증가분은 처음부터 5xx 건수와 정확히 맞았기 때문에, 두 지표를 함께 기록한 덕분에 잡을 수 있었다. 고친 뒤 지난 회차는 요청 시각 구간으로 로그를 다시 걸러 재계산했고, 모든 조건에서 두 지표가 일치했다.

**교착이 생기는 원리 확인 (InnoDB 덤프)**
- 리뷰 경로 덤프에서 두 트랜잭션이 같은 `recipe` 행에 **S 레코드 락(gap 아님)을 쥔 채 X 락을 기다리고** 있었다(`lock mode S locks rec but not gap` / `lock_mode X … waiting`). 리뷰 INSERT의 외래 키 검사가 부모 행에 S 락을 걸고, 이어지는 카운터 UPDATE가 X 락으로 올리려다 서로 막힌다.
- 기존 필기에 적었던 "INSERT의 gap lock 때문"은 덤프와 다르다. 정정했다.

**결과 (A: 같은 레시피 100명, 워밍업 제외 4회)**

| 변형 | 성공 / 100 | 교착 | p95 (회차 median) |
|---|---|---|---|
| v0 INSERT → UPDATE | 6 (5~8) | 94 (92~95) | 924ms (대부분 일찍 실패해서 낮음) |
| v1 FOR UPDATE | 100 | 0 | 2,001ms |
| v3 UPDATE 먼저 | 100 | 0 | 1,856ms |

- 교착은 **10명부터** 시작됐고(8건 실패), 4개 경로 모두 같은 구조로 재현됐다.
- 서로 다른 레시피(B)에서 v3는 느려지지 않았다(p95 644 → 356ms).
- 실패한 요청은 롤백되므로 카운터는 실험 1 전체 228회(워밍업 포함) 모두 실제 행 수와 일치했다. 즉 이 문제는 "데이터 유실"이 아니라 **"요청 실패"**다.

**정합성 검사로 찾은 버그: 평균 별점이 절반으로 저장된다**
- B 시나리오(레시피당 리뷰 1건)에서 v3의 평균 별점이 **100개 중 100개** 틀렸다. 2·3·4·5점이 1·1.5·2·2.5로 저장됐다.
- 원인을 추적했다. `SET reviewCount = reviewCount + 1, avgScore = (avgScore × reviewCount + s) / (reviewCount + 1)`에서 MySQL은 SET 절을 **왼쪽부터 평가**하므로, 평균 계산에 이미 1 늘어난 리뷰 수가 쓰인다. 임시 테이블로 직접 확인했다(4점 리뷰 1건: 기존 순서 2, 고친 순서 4).
- 커밋 이력상 두 UPDATE를 하나로 합친 `dd06895`에서 처음 들어갔다.
- SET 순서를 바꾼 수정 커밋(`0914ab8`)을 만들고 v4로 다시 측정했다. 불일치가 100 → **0**으로 사라졌다.
- 남은 문제도 하나 확인했다. 리뷰 100건이 쌓이면 평균이 0.1~0.2 어긋난다. 매번 반올림한 평균을 다음 계산에 다시 쓰는 **반올림 누적 오차**다. 고치려면 스키마 변경이 필요해 기록만 했다.

**의심한 것: 버전 간 지연 비교는 락 순서만의 효과가 아니다**
- v0·v1·v3는 서로 다른 커밋이라 락 순서 말고도 쿼리 수 등이 다르다. 경합이 없는 시나리오 B에서도 p95가 달랐던 것(v0 644ms, v3 356ms)이 그 증거다. 그래서 성공률·교착 건수 결론은 유지하되 "v3가 v1보다 몇 % 빠르다"는 지연 비교는 근거에서 뺐다. 처음에 "7~27% 개선"이라고 쓴 것은 철회했다(찜 50명은 4회 합산 p95가 810ms 대 796ms로 같았다).
- **같은 코드에서 락 순서만 바꿔 다시 쟀다.** v4 위에 `insert_first` / `for_update` / `update_first` 모드를 환경변수로 넣었다(메인 코드에는 넣지 않음). 5라운드, 모드 순서 회전, 1회차 워밍업 제외.

| 시나리오 | FOR UPDATE | UPDATE 먼저 | 차이 |
|---|---|---|---|
| 같은 레시피 리뷰 100명 | 1,816ms (1,708~1,880) | 1,559ms (1,456~1,630) | **−14%** |
| 찜 100명 | 1,496ms (1,488~1,507) | 1,284ms (1,240~1,354) | **−14%** |
| 찜 50명 | 726ms (705~746) | 611ms (598~660) | **−16%** |
| 서로 다른 레시피(경합 없음) | 369ms | 358ms | 차이 없음 |

- 성공률·교착은 락 순서가 결정했다(INSERT 먼저만 6~8/100 성공, 교착 92~94). 회차 범위가 겹치지 않고, 경합이 없을 때는 차이가 없어 락 순서의 효과로 해석한다. 기존 "4.65 → 0.92초(약 80% 개선)"는 재현되지 않았고 실제 개선은 14~16%다.

**남은 오차도 직접 확인했다 (평균 별점 반올림 누적)**
- v4는 평균을 반올림해 다음 계산에 다시 쓰므로 오차가 쌓인다. 사용자 100명이 레시피 20개에 2,000건을 동시에 쓰게 했더니 **레시피 12~13개(60~65%)의 평균이 어긋났고** 최대 오차는 0.2였다(리뷰 수는 정확).
- 점수 합계(`score_sum`)를 저장하고 평균을 합계/개수로 계산하는 변형(컬럼 하나와 UPDATE 쿼리 변경)을 같은 조건으로 3세트(6,000건) 재니 **불일치 0, 오차 0.0**이 됐다. 실험용 변형이며 메인 코드에는 아직 반영하지 않았다.

**추가로 물은 것: 선잠금 외에 다른 방법은 정말 안 되나 (재시도 비교, 두 번 측정)**
- 원래 시도했던 재시도 코드는 커밋된 적이 없어 재현할 수 없다. 그래서 v0 위에 재시도 모드를 새로 구현해 비교했다(옛 58/100의 검증이 아님).
- **처음에는 고정 짧은 대기(10~50ms)로 재서 "재시도는 10회로도 66건뿐, 교착 시도 7배"라고 결론 냈다. 그런데 리뷰에서 "재시도 설계가 약했다"는 반박이 나왔고, 지수 백오프로 다시 재니 결과가 크게 달랐다.** 이 과정에서 결론이 바뀐 것이 이번 재검증의 중요한 교훈이다.

| 방식 | 성공 / 100 | 교착 시도 | p95 (회차 median) |
|---|---|---|---|
| 재시도 없음 | 6 | 94 | 924ms |
| 같은 트랜잭션 안, 3회 | 5~8 | 260 | 약 1.0~1.1초 |
| 트랜잭션 밖(새 트랜잭션), 3회, 고정 대기 | 18 | 268 | 1,181ms |
| 트랜잭션 밖, 3회, 지수 백오프 | 24 | 256 | 1,329ms |
| 트랜잭션 밖, 10회, 고정 대기 | 66 | 666 | 2,428ms |
| **트랜잭션 밖, 10회, 지수 백오프** | **98 (95~100)** | 294 | **6,386ms** (3.7~8.8초) |
| **UPDATE 먼저** | **100** | **0** | **1,559ms** |

- **같은 트랜잭션 안 재시도는 구조상 불가능하다.** 재시도 때마다 트랜잭션 상태를 로그로 남겨 확인했다. 262번 모두 `rollbackOnly=true`였다. 교착 예외가 저장소 호출을 지나는 순간 Spring이 트랜잭션을 롤백 전용으로 표시하기 때문이다. 교착을 겪은 요청 96건 중 81건은 3회를 소진해 실패했고, 15건은 재시도가 성공한 것처럼 보였지만 커밋에서 `UnexpectedRollbackException`으로 실패했다(96 = 81 + 15). 처음에 이 예외가 0건이라고 쓴 것은 오류 줄만 걸러 저장한 로그를 센 실수였다.
- **밖에서 재시도하면 성공이 늘고 대기 설계가 결과를 좌우한다.** 지수 백오프 10회로는 98/100까지 올라간다.
- **그래도 락 순서 변경이 낫다.** 지수 백오프 10회도 최대 5건이 여전히 실패하고, 교착 시도가 294건이며, p95가 6.4초로 락 순서 변경(1.6초)의 약 4배다.

### 3.2 실험 2 — ES+Nori는 무엇을 개선했나

**질문**: ES 도입으로 정말 빨라졌나? 오타 보정은 우연히 몇 개 맞은 것이 아닌가?

**설계에서 고민한 것**
- **API가 아니라 검색 계층에 직접 질의했다.** 검색 API는 외부 식품안전나라 API(로컬에서는 더미 키) 호출과 변형 레시피 병합까지 해서, 정답률과 지연이 오염된다. 앱과 같은 쿼리를 MySQL과 ES에 직접 보냈다. boost는 코드에 3.0으로 고정돼 있어서, 민감도를 보려면 이 방법밖에 없었다.
- **오타를 사람이 고르지 않았다.** 사람이 고르면 잘 맞는 오타만 고르게 된다. 시드를 고정해 음식명 200개를 뽑고, 6가지 유형(모음 치환, 쌍자음 탈락·추가, 초성 치환, 받침, 음절 누락)으로 오타를 자동 생성했다.
- **오타는 제목이 아니라 음식명에 넣었다.** 사용자는 "부산식 소불고기덮밥"이 아니라 "소불고기덥밥"으로 검색한다.
- **편집 거리를 ES와 같은 정의로 맞췄다.** ES fuzziness는 인접 문자 교환도 거리 1로 친다. 그래서 자모 1/2/3 구간이 ES 기준과 일치하도록 했다.
- **정답 기준을 두 개 뒀다.** 같은 음식명 레시피가 여러 개라 "원래 ID가 5위 안"(엄격)은 과소평가된다. 그래서 "상위 결과에 원래 음식명 포함"(느슨)을 대표로 쓰고, 엄격은 참고용으로 뒀다.

**채점기에서 찾은 버그**: 엄격 기준이 ES에서만 전부 0%였다. ES 문서의 type이 대문자(`RECIPE`)인데 소문자로 비교했기 때문이다. 고친 뒤 전체를 다시 채점했다.

**결과**

| 자모 수정 | LIKE | FULLTEXT | ES+Nori | ES+Nori+Jamo |
|---|---|---|---|---|
| 1곳 | 0% | 0% | 57.5~64.5% | **99.5~100%** |
| 2곳 | 4.5~8.5% | 4.5~8.5% | 30.5~32.5% | **93.5~96%** |
| 3곳 (예상 실패 구간) | 6.5~10% | 7~10% | 24~28.5% | 19.5~27% |

- 기존 질의 세트로는 오타 1위 20/20, 처음 보는 오타 12/12로 **자모 적용 후 수치는 기존 주장과 일치**했다. 다만 자모 적용 **전** 수치는 기존 7/20, 3/12가 아니라 8/20, 4/12였고, 정상 검색 P@5도 기존(LIKE 99.4%, ES+자모 97.6%)과 달리 LIKE 96.5%, ES+Nori 97.6%, ES+자모 98.2%였다. 기존 비교 대상이 달라 "일치"가 아니라 **"수치가 바뀜, 방향은 같음"**으로 판정한다. 측정 방식(기존은 검색 API 경유, 이번은 DB·ES 직접 질의)과 시드 변동 영향도 있다.
- 오타 구간 표의 "거리" 칸에는 오타 유형 구성이 섞여 있었다. LIKE가 맞힌 오타는 **전부 음절 누락이 섞인 경우**였고, 자모만 고친 오타는 거리와 무관하게 0%였다(LIKE가 자모 2곳에서 4.5~8.5%인 이유). 유형별로 나눠 보면 ES+자모는 "자모만 고친 오타" 1곳 100%, 2곳 95%, 3곳 18%다.
- 지연은 달랐다. 5,000건에서 ES는 LIKE보다 빠르지 않았다(10 VU p95 98 vs 87ms). 50,000건 50 VU에서만 LIKE가 1.17초로 급락했고 ES는 0.26초였다. FULLTEXT는 지연이 ES와 비슷하거나 빨랐지만 오타 보정은 못 했다.
- 자모 필드는 ES 엔진 처리 시간을 약 2ms → 18ms로 늘렸다. API 전체 응답(약 100ms)에 비하면 작다.
- boost는 3부터 효과가 포화됐다(2는 자모 2곳 91.5%, 3 이상 93.5%). 정상 검색 P@5는 boost 1 이상에서 98.2%로 변하지 않았다. 이 표로 boost를 다시 고르지는 않았다. 같은 데이터로 고르면 과적합이기 때문이다.

**외부 호출을 없애고 다시 쟀다 (stub)**
- 검색 API는 요청마다 외부 식품안전나라 API를 부르는데 주소가 코드에 박혀 있다. 코드를 고치지 않고 컨테이너 호스트 매핑(`extra_hosts`)으로 호스트의 가짜 서버(20ms 고정 지연)에 연결했다. 5,000건, 엔진 3종 × 10·50 VU × 1분 × 4회(워밍업 제외 3회).
- p95(median): 10 VU는 FULLTEXT 62ms < LIKE 79ms < ES 95ms, 50 VU는 FULLTEXT 146ms < LIKE 189ms < ES 201ms. 1분 처리 요청 수도 FULLTEXT 18,694 > LIKE 15,021 > ES 11,559(10 VU)였다. **외부 API 호출이 엔진 간 차이를 가렸던 것이 아니다.** ES는 5,000건에서는 가장 느리고, 이유는 속도가 아니라 오타 보정이다.

**"49% 개선"과 왜 달랐나**
- 기존 필기의 "도입 전"은 ES 인덱스를 지워 *ES 호출이 실패한 뒤 LIKE로 전환되게* 만든 상태였다. 실패 처리 시간까지 "LIKE의 시간"에 섞였을 가능성이 크다. 이번에는 LIKE 엔진을 직접 써서 기존 스크립트로 다시 쟀고, LIKE 25.2ms, ES 26.7ms로 차이가 없었다.
- 이 대조의 첫 실행은 메모리 압박으로 시스템이 불안정하던 시점이라 MySQL은 51% 실패, ES는 요청 1건에서 중단됐다. 같은 부하로 재현해도 실패가 나오지 않아 무효로 처리하고, 5,000건 복원 뒤 다시 쟀다. 이후로는 실패율 1% 초과면 기록하지 않도록 검증을 넣었다.

**결론**: ES+Nori+Jamo의 근거는 속도가 아니라 **오타 보정**이다. 속도만 원했다면 FULLTEXT로 충분했을 것이다.

### 3.3 실험 3 — 추천 캐시는 효과가 있고, 장애에도 안전한가

**설계**
- cold는 키를 지우는 대신 **한 번도 요청하지 않은 사용자 1,000명**이 한 번씩 요청해 만들었다. 50 VU에서 매번 키를 지울 수는 없기 때문이다.
- warm은 사용자 100명 × 추천 4종 키를 미리 채우고, 인기 사용자에게 몰리는 Zipf 분포(s = 1.0)로 요청했다.

**측정 실패에서 배운 것**: 적중률이 전부 0으로 기록되고 있었다. 앱에 Redis 캐시 통계가 꺼져 있어 Micrometer `cache.gets`에 값 자체가 없었다. 코드를 고치지 않는 원칙이라, 측정 직전에 Redis `CONFIG RESETSTAT`을 실행하고 추천 API만 호출한 뒤 `INFO`를 읽는 방식으로 바꿨다. 0으로 들어간 행 80개는 지웠다.

**결과**
- 적중률: cold 0%, warm 100% (3회 모두 동일). **이 값은 실험 설계가 정한 것**(cold는 처음 보는 사용자, warm은 미리 채운 키)이라 성과로 쓰지 않는다. 의미 있는 수치는 응답 시간 차이와, 빈 캐시에서 실제와 비슷한 트래픽을 흘렸을 때 적중률이 시간에 따라 오르는 곡선이다(아래 추가 측정).
- 응답: avg 1 VU 16.5 → 2.6ms(약 6.3배), 50 VU 82.4 → 20.9ms(약 3.9배).

**의미 있는 적중률은 어떻게 구하나 (빈 캐시 + Zipf 트래픽)**
- 0%/100%는 설계값이라 성과가 아니다. 빈 캐시에서 Zipf(s = 1.0) 트래픽을 30 RPS로 7분(12,600건, 키 4,000개) 흘리며 10초 창마다 적중률을 읽었다. 창 안의 적중률은 Redis 조회 수와 요청 수의 차이(미적중 1건당 알레르기 캐시 조회가 1회 더 생김)로 계산했다.
- 0~60초 51% → 60~180초 73% → 180~300초 **81%(최고)** → 300~420초 74%. 5분 시점부터 처음 채워진 키의 TTL(5분)이 만료돼 적중률이 내려가는 톱니 모양이 보였다. TTL을 늘리면 적중률은 오르지만 무효화 지연과 맞바꾸게 된다.

**캐시 무효화가 커밋 전에 일어나지는 않는가**
- 찜을 추가한 직후 50ms 간격으로 추천을 조회하는 동안, 다른 스레드가 10ms 간격으로 같은 캐시를 계속 읽게 했다. 커밋 전에 캐시가 지워지면 이 읽기가 옛 값을 다시 캐시에 넣어, TTL(5분) 동안 옛 값이 남는다.
- 50회 중 영구 stale은 **0건**이었다. 새 값이 보일 때까지 p50 34ms, p95 74ms였다. 커밋 뒤에 Kafka로 무효화를 보내는 구조가 작동하고 있었다.

**장애를 주입하자 드러난 약점**
- Redis를 멈추자 추천 API 40건이 **전부 응답 없이 30초 넘게 매달렸다.** 오류를 돌려주지도 않았다.
- 코드를 확인하니 캐시 오류 처리기와 Redis 명령 타임아웃 설정이 없었다. 캐시가 죽으면 DB로 우회하지 못하고 클라이언트 기본 타임아웃(60초로 추정)까지 기다리는 것으로 보인다.

### 3.4 실험 4 — 커넥션·스레드 풀 튜닝은 정말 처리량을 늘렸나

**1차 측정과 그 결론을 버린 이유**
- 처음에는 요청률 방식으로 설정 5종을 잰 결과 SLO 최대 RPS가 회차마다 200~600으로 출렁여 "튜닝 효과 불분명"이라고 결론 냈다. 그런데 포화 구간 실패 187만 건이 **전부 연결 거부·강제 종료였고 5xx는 0건**이었다. 요청이 Windows의 Docker Desktop 포트 포워딩(`127.0.0.1:8080`)을 지나므로 앱이 아니라 로컬 네트워크 계층의 한계를 쟀을 가능성이 컸다.
- 단계가 2배씩 뛰고(200→400→600), 실패 요청이 0ms로 p95에 섞이며, 식단 API 404와 첫 회차 워밍업도 섞여 있었다. 1차 결과는 **폐기**하고 부록으로 옮겼다.

**재설계**
- k6를 Docker 네트워크 안 컨테이너로 실행(포트 포워딩 경로 제거), 300~600 RPS를 50 단위로, **성공 응답만으로 p95 계산**, 식단 데이터를 미리 넣어 404 제거, 외부 API는 stub으로 고정, 매 회차 컨테이너를 새로 띄우고 예열, 1회차는 워밍업으로 제외하고 설정 3종(기본값, Hikari만, 전체 튜닝) × 3회를 집계했다.
- 중간에 노트북이 4시간 넘게 절전에 들어가 한 회차가 무효가 됐고(Windows 로그로 확인), 그 회차를 분리해 다시 쟀다.

**결과**
- 63개 단계 전체에서 **5xx·연결 실패·404·비200이 0건**이었다. 1차의 연결 거부는 포트 포워딩 경로가 만든 것이었고, 포화는 지연 증가와 k6 드롭으로 나타난다.
- 300 RPS 단계는 350보다 느리게 나와 **회차 안 추가 워밍업 구간**으로 보고 연속 통과 지표에서 뺐다.

| 설정 | SLO 통과 최고 RPS (3회) | 500~600 RPS 통과 | 600 RPS p95 median |
|---|---|---|---|
| 기본값 | 550 (500, 550, 550) | 5/9 | 1,498ms (0/3 통과) |
| Hikari만 | 500 (500, 600, 350) | 4/9 | 1,600ms (1/3) |
| **전체 튜닝** | **600** (600, 600, 600) | **8/9** | **590ms (3/3)** |

- **기본값은 600에서 무너지고**, 그때 Hikari 풀 10개가 포화돼 Tomcat 스레드가 커넥션을 기다린다(대기 198, 앱 CPU 445%로 제한 미만 → 병목은 풀).
- **전체 튜닝은 600에서 3/3 통과(p95 359~629ms)**로 기본값(1,117~2,423ms)과 범위가 겹치지 않는다. 이때 앱 CPU가 629%로 제한(600%)에 닿아 병목이 **풀에서 CPU로 이동**했다.
- **Hikari 풀만 키운 설정은 기본값보다 나아지지 않았다**(통과율 56%). 풀만으로는 부족하고 Tomcat 스레드·대기열이 함께 필요했을 가능성이 있다. 다만 Tomcat만 바꾼 설정은 재설계에서 재지 않아 항목별 기여도는 단정하지 못했다.
- **한계**: 600이 최고 단계라 튜닝 설정의 상한을 모른다. 설정당 3회라 퍼센트 개선 폭은 말하지 않는다. 커넥션 점유 시간(풀 크기 대신 누가 오래 쥐는지)은 이번에 재지 못했다.
- 기존 VU 방식(3,000 VU)도 CPU 제한 없이 설정당 2회로 다시 잰 결과는 기본값 848, 튜닝 818 RPS(실패율 49~60%)로 "733 → 1,012(+38%)"가 재현되지 않았다. 실패 요청이 빨리 끝나 RPS가 부풀려지는 구조라 이 방식의 RPS는 성능 지표로 쓰지 않았다(부록).

**약점을 고쳐 보고 다시 쟀다 (두 번 고친 이야기)**
- 기준선: Redis를 멈추고 추천 5건을 보내자 **정확히 60.1초 뒤 500**이었다(Lettuce 기본 명령 타임아웃 60초). 부하 중에 30초 동안 Redis를 내리면 **전체 요청의 95~97%가 실패**했고, Redis와 무관한 상세·식단도 84~93%가 실패했다. 추천이 스레드를 60초씩 붙잡아 다른 API까지 굶긴 것으로 해석한다.
- **1차 수정은 틀렸다.** `CacheErrorHandler`만 추가하고 Redis 타임아웃을 200ms로 줄였더니 상세·식단은 살아났지만(0%) 검색·추천은 **100% 500**이었다. 실패율은 69~72%였고 복구 뒤에도 11~12%가 실패했다. 캐시 매니저가 `transactionAware`라 저장·삭제가 커밋 뒤에 실행되는데, 그때의 예외는 `CacheErrorHandler`를 거치지 않기 때문이라고 추정했다(스택으로 확인하지는 않음).
- **2차 수정**은 캐시 자체를 감싸는 `FailureTolerantCache`를 트랜잭션 데코레이터 안쪽에 끼웠다. 장애 중 실패율 **0~0.2%**, 복구 즉시 정상이었다. 대신 장애 중 성공 응답의 p95가 25ms에서 0.9~1.6초로 느려졌다(DB 우회와 200ms 연결 타임아웃). 이 대가를 숨기지 않고 보고서에 썼다.
- 배운 점: 단위 테스트만 통과하는 수정은 믿으면 안 된다. 1차 수정도 단위 테스트는 통과했고, 부하 중 장애 주입을 해서야 실패가 드러났다.

**커넥션을 누가 쥐나: 결론을 세 번 뒤집은 이야기 (#24)**
1. **처음 결론**: 검색이 요청당 커넥션을 2번 빌리고 건당 약 230ms 쥐어서 100 RPS에서 풀이 포화한다고 보았다. 리뷰가 "실험 4는 600 RPS를 통과하는데 왜 검색 100 RPS에서 무너지나"라고 물었고, 실험 4의 검색어가 7개 반복이라는 점에서 "캐시 미적중" 조건을 따로 만들었다.
2. **첫 번째 오염**: 수정 전/후를 쟀더니 효과가 없는 것처럼 나왔는데, 같은 이미지가 회차마다 217 → 167 → 105ms로 줄었다. "미적중" 검색어(난수 4자리)가 63,000개 조합뿐이라 Redis 캐시(TTL 1시간)가 쌓이며 적중이 섞이고 있었다. 검색어를 실행마다 유일하게 바꿔 다시 쟀다.
3. **원인 추적**: 다시 재도 수정만으로는 점유가 그대로였다. 스레드 덤프를 뜨니 수정 전에는 트랜잭션 안에서 외부 API·ES·Redis 응답과 재시도 대기가 커넥션을 쥐고 있었고(MySQL은 놀고 있음), 수정 후에는 요청 스레드가 쥔 표본이 거의 없는데도 점유가 그대로였다. OSIV를 끄니 둘을 함께 할 때만 점유가 330ms → 18~80ms로 줄었다. 여기까지는 "원인을 찾았다"는 이야기였다.
4. **두 번째 오염 (가장 큰 정정)**: 3.5초대 꼬리 지연이 남아서 원인을 파고들었다. 느린 요청 43건이 외부 API `Connect timed out` 후 재시도로 성공한 43건과 정확히 일치했다. 컨테이너 → 호스트 stub 경로 자체는 단독으로는 멀쩡했지만 앱과 함께 돌 때만 연결 시간 초과가 났다. **stub을 도커 네트워크 안으로 옮기자 포화가 사라졌다**(풀 대기 1.1~1.8초 → 5~6ms, 요청 평균 2.7~5.5초 → 128~137ms). 즉 "캐시 미적중 검색이 풀을 포화시킨다"는 결론 전체가 **내 테스트 환경의 연결 시간 초과와 재시도가 만든 현상**이었다. 이미 머지한 보고서 수치를 정정했고, 오염된 행은 지우지 않고 `*_hoststub_artifact`로 표시해 남겼다.
5. **그래서 무엇이 남았나**: (a) 외부 호출이 읽기 트랜잭션 안에 있다는 **코드 구조**는 사실이고 스레드 덤프로도 보였다. (b) 정상 환경에서도 요청당 커넥션 점유 합은 약 2.8배 줄었다(137~150ms → 52~56ms). 다만 사용자 지연은 같다. (c) **외부 API를 300ms로 느리게 한 조건**에서는 수정 전이 점유 약 450ms, 풀 대기 50~92ms, p95 1.2~1.7초로 나빠지지만 수정 후는 변함이 없다(p95 약 480ms). 그래서 이 수정의 가치는 "지금의 풀 포화 해결"이 아니라 **"외부 API가 느려질 때 풀이 따라 포화하지 않는 여유"**다.
6. **교훈**: 극적인 결과(포화)가 나오면 먼저 측정 도구를 의심한다. 이번에 걸림돌이었던 것: 캐시가 쌓이는 검색어, stub의 연결 경로, 부하 중 ES 서킷 우회(요청의 25~49%가 MySQL로 우회). 비교 실험은 같은 경로를 타는지(캐시 적중, 서킷 우회, 재시도 횟수)를 회차마다 세어 두어야 한다. 정정을 세 번 한 것은 부끄러운 일이 아니라, 정정할 수 있게 원본을 남기고 있었다는 증거다.
7. 남은 것: ES 서킷이 부하 중 왜 열리는지(미확인), 나머지 쓰기 API에서 OSIV를 꺼도 괜찮은지(GET 23개·쓰기 8개는 이상 없음), 코드 변경과 OSIV 끄기의 몫 분리(정상 환경에서는 측정하지 않음).

**MySQL만으로 오타 검색이 되나 (자모 컬럼 + FULLTEXT)**
- "ES가 아니면 안 되나?"라는 반론에 컬럼 하나와 ngram 인덱스로 답했다. 자모 1곳 오타는 **89~93%**를 맞혔다(ES 99.5~100%). 3곳에서는 오히려 MySQL(54~70%)이 ES(14~27%)보다 높았다. ES의 근거는 "유일한 방법"이 아니라 "1~2곳에서 7~20%p 더 정확하다"로 좁혀졌다.

### 새로 발견한 것

1. **평균 별점 절반 저장 버그**: SET 절 평가 순서 때문. 수정 커밋 `0914ab8`, 불일치 100 → 0.
2. **평균 별점 반올림 누적 오차**: 100건에서 0.1~0.2 (미수정).
3. **Redis 장애가 서비스 전체로 번짐**: 60.1초 뒤 500, 중단 중 전체 요청 95~97% 실패. 2차 수정(별도 브랜치, PR 전)으로 0~0.2%, 단 장애 중 p95 0.9~1.6초.
6. **검색은 외부 API 응답을 기다리는 동안 커넥션을 쥐는 구조**: 정상 환경에서는 풀을 포화시키지 않지만(앞선 "포화" 보고는 내 테스트 환경 산물로 정정), 외부 API가 300ms로 느려지면 점유가 약 450ms로 늘어난다. 트랜잭션 범위 축소 + OSIV 끄기는 이를 막는다(PR #26).
7. **MySQL 자모 FULLTEXT로도 자모 1곳 오타 89~93%**: ES 도입 근거를 정직하게 좁힘.
4. **측정 도구의 왜곡**: `shared-iterations`의 중복 요청, 로그 시간대 오류, 실패 요청이 RPS를 부풀리고 p95를 낮추는 효과.
5. **찜 추천 정렬 코드**: `.reversed()`가 연속 호출돼 동점일 때 평균 별점이 오름차순이 된다(미수정, 범위 밖).

## 5. 이 과정에서 세운 원칙

1. **측정 도구도 의심한다.** 이번에 찾은 문제 중 두 개(중복 요청, 로그 시간대)는 앱이 아니라 측정 도구에 있었다.
2. **한 현상을 두 출처로 확인한다.** InnoDB 카운터와 앱 로그를 함께 두지 않았다면 로그 집계 버그를 결과로 믿었을 것이다.
3. **실패한 요청이 지표를 어떻게 바꾸는지 먼저 본다.** 실패가 많으면 RPS는 부풀고 p95는 낮아진다. 성공 응답 기준 지표를 따로 둔다.
4. **확정과 가설을 구분해서 쓰고, 한 설정의 결론을 일반화하지 않는다.** 재시도의 rollback-only는 로그로 확인하기 전까지 가설이었고(이제 확정), "재시도는 10회로도 66건뿐"은 고정 대기 한 가지 구현의 결과였다(지수 백오프로는 98건).
5. **결과가 기대와 달라도 기록한다.** 이번 재검증에서 기존 수치 다섯 개가 재현되지 않았고, 그 사실 자체가 가장 많은 것을 알려 줬다.

## 6. 다음에 이어서 물을 것

- **장애 격리 확대**: Redis는 끝냈다. ES·Kafka를 부하 중에 내려 전파를 재고, Redis 알림 Pub/Sub 경로도 확인한다.
- **진짜 병목**: k6를 Docker 네트워크 안에서 실행해 연결 거부가 로컬 계층 때문인지 확인한다. 외부 API를 고정 지연 stub으로 바꾼 뒤 프로파일링(JFR)으로 CPU 사용처를 찾는다.
- **남은 쓰기 경합**: 같은 레시피에 몰릴 때 p95 1.86초의 원인인 잠금 보유 시간을 줄인다. 잠금이 필요 없는 조회를 UPDATE 앞으로 옮기는 방식이다.
- **반올림 누적 오차**: 점수 합계를 저장해 오차 0을 검증한다.

## 7. 자소서·면접용 요약
